# Git 开发、提交与发布流程

## 当前分支职责

| 分支 | 起点 / 当前内容 | 后续用途 |
| --- | --- | --- |
| `dev` | 已公开的 `0.5.0-pre`，以及之后的开发与治理修复 | 集成功能和普通修复，生成开发快照 |
| `main` | 保留已公开的 `0.5.0-pre` 历史 | 只集成已验证的 dev，并提交版本元数据、变更记录和发布制品 |
| `maintenance/0.4` | 稳定 Tag `v0.4.0` 的 `cea4e90` | 单独维护已交付的 0.4 版本 |
| `feature/*` / `fix/*` | 从 `dev` 派生 | 一项功能或修复完成后合回 `dev` |
| `refactor/*` / `milestone/*` | 从 `dev` 派生 | 共享服务重构、开发计划及里程碑验证，完成后合回 `dev` |
| `hotfix/*` | 从对应稳定 Tag 或已有维护线派生 | 紧急修复，之后同步到适用的开发线 |

`main` 历史上已经包含并发布 `0.5.0-pre`，本次保留该事实。最新正式版是
`v0.4.0`，维护它时使用 `maintenance/0.4`。不要为了让 main 看起来只含稳定版
而回退公开分支，也不要为历史补造 merge commit。

两个原有功能分支曾使用 fast-forward 合并，因此历史图为线性；这种历史有效。
从本次治理开始，真实的跨分支集成使用 `--no-ff`，让合并边界可见。

根据维护者最新指令，后续功能、修复、文档和仓库规则均先在从 `dev` 派生的
分支开发并合回 `dev`，不能直接在 `main` 实施。`main` 只负责集成验证完成的
版本范围和提交版本号等发布准备内容；此前的治理提交保留为历史事实。
有依赖的分支等待前置工作合回 `dev` 后，再从更新的 `dev` 创建。
当前开发计划见 [0.5.0 开发计划](PLAN_0.5.0.md)。

## 日常开发与提交

```bash
git switch dev
git switch -c feature/describe-the-change
# 实施一项变化并进行相关验证。
git add path/to/changed-file
git diff --cached
git diff --cached --check
git commit -m "feat(module): describe the observable change"
git switch dev
git merge --no-ff feature/describe-the-change
```

代码修复使用 `fix(module): ...`；文档使用 `docs: ...`；main 上的版本元数据准备使用
`chore(release): prepare vX.Y.Z`。破坏性变更使用 `!` 或 `BREAKING CHANGE:`
并说明迁移方式。不要为了让 CI 忽略用户可见变化而标成 `chore`。

合并信息保留实际变化语义；如果已有工具改用 squash，最终 squash 提交必须保留
`feat`、`fix` 和破坏性标记。多个独立变化分开提交；同一变化的源码与测试一起提交。
暂存和提交前确认没有带入其他任务的内容。

## 本项目的早期版本策略

本项目仍为 `0.x`，从本次治理开始明确以下约定，旧版本编号保持不变：

- 只有兼容修复：升级 PATCH，例如维护线 `0.4.0 → 0.4.1`。
- 新增兼容功能、兼容弃用或不兼容接口变化：升级 MINOR、清零 PATCH。
  0.x 的不兼容变更仍须显式标记并说明迁移；不会自动视为已承诺稳定 API 的 `1.0.0`。
- `1.0.0` 表示建立稳定公共接口的承诺，由维护者明确决定。
  此后按 SemVer 使用 MAJOR / MINOR / PATCH。
- 一批变化只升一次，取最高等级，不按 Bug 数、提交数或 CI 重试数计算。
- 只有无发布语义的文档、测试和 CI 配置变更时，不创建新的业务版本。

`0.5.0-pre` 已经是公开预发布版本，保持其 Tag、版本和制品。
后续普通快照可采用 `0.5.0-dev.N` 并记录源码 SHA，默认不打永久 Tag，
通过临时构建元数据或构建注入标识，不为每次开发提交修改受版本控制的正式版本字段；
这是开发通道，SemVer 中 `dev.N` 排序低于已有的 `pre`，不要把它称为更高的预发布版本。
若继续向预发布用户交付，则按确定的版本策略使用后续预发布号（如 `0.5.0-pre.1`），
不覆盖已分发的 `0.5.0-pre`。功能范围不变时，完成这一轮可定版 `0.5.0`。

## 定版、Tag 与 Release

1. 固定目标版本线与源码 SHA，确认历史和远端 Tag 已完整读取。
2. 从该线的上一正式 Tag 起计算新增变化，包括尚未 Release 的正式 Tag；
   排除其他维护线和快照 Tag。预发布最终转正式时，按同一正式基线聚合变化，
   不把预发布次数当 PATCH 次数。
3. 验证选定范围在 `dev` 完成后，再把该范围真实合入 `main`。
   功能、修复和普通文档提交已经在开发分支完成，main 不临时补做这些开发。
   旧版维护在对应维护线上定版。
   执行验证，更新 `package.json`、`src/index.ts` 中插件版本及 CHANGELOG。
   锁文件按实际已有字段同步版本：当前为顶层 `version` 与 `packages[""].version`。
   不为没有相应版本字段的锁文件凭空新增字段。
4. 从最终源码构建并核实 dist、插件元数据和必要的版本化导出，提交全部版本准备内容，
   再在该最终提交上创建 annotated Tag。已有工具或签名要求优先。
5. Tag 创建后保持不变。普通准备提交不等于 Release；维护者选择已有 Tag 分发。
6. 在干净、隔离的目录检出指定 Tag 对应的 SHA，执行 `npm ci`、`npm run check`。
   发布记录保存 Tag、完整 SHA、制品版本和 SHA-256。
   已有从同一 Tag 构建且来源、摘要均验证的制品时可以复用。
7. Release 使用既定版本，不再 bump；修复已经分发的内容需要新的版本。

当前历史的 `v0.2.1` 存在本地/远端冲突，禁止以它直接进行可靠重构。
`provenance/v0.2.1-asset` 仅记录当时发布 JS 的实际来源，不属于新的正式版本 Tag，
不得作为版本计算基线。具体 SHA 和摘要见 [历史审计](GIT_HISTORY_AUDIT.md)。

## 旧版本修复

从 `maintenance/0.4` 建修复分支，只带兼容修复和必要测试。
在该线定版 `0.4.1` 后，将实际修复同步到 `dev` 和适用的 `main`。
新功能继续沿 `dev` 推进；不能把 0.5 的网页/移动端支持带入 0.4 的 PATCH。
是否紧急不决定版本等级，计划内维护也可以是 PATCH。

## CI 与远端操作

- 版本计算与 Tag 分配按产品、版本线串行化，并重新读取远端状态。
- 同一待定版源码 SHA 的重试复用版本，记录业务源码与最终定版提交的对应关系。
- 已存在 Tag 完全一致则复用，冲突则停止；不得靠移动 Tag 或再升版本掩盖冲突。
- 只更新版本的准备提交不要再触发一次定版；自动化不因创建 Tag 就自动 Release。
- 当前仓库尚未实现自动定版 CI；这些是实现约束，不能宣称它们已经自动执行。
- 推送时指定分支和必要的 Tag。当前 `v0.2.1` 冲突未解决前，禁止 `git push --tags`。
- 本地将 `main`、`dev` 和维护线的默认合并选项设为 `--no-ff`；此配置不替代
  GitHub 上的合并策略、分支保护或审核，远端配置变更须有相应授权。

参考 [Conventional Commits](https://www.conventionalcommits.org/zh-hans/v1.0.0/)、
[SemVer](https://semver.org/lang/zh-CN/) 和 [Git 合并文档](https://git-scm.com/docs/git-merge)。
